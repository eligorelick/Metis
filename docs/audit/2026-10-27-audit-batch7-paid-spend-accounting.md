## Limits and residuals

1. **An idle stream with no reported usage is presumed at the request maximum** (OD-2). Before this batch the idle guard presumed only the output remainder in that state. A stream that went silent before reporting any usage is therefore recorded at the whole request maximum, even if little or nothing was billed, until `costs:reconcile` or a late settlement lowers it. Reversible as described under OD-2.
2. **The assembly-rejection record is process-only** (AI-112, RPT-210). Judge attempts rejected at report assembly are listed in the running process. A crash-recovery rebuild reads the marks stored in the pass artifacts but does not mark an assembly rejection. A reused durable artifact is never marked.
3. **OD-5's three residuals** (JOB-203). Anthropic documents neither attribution instant for a request. (a) If a request measured across 00:00 UTC is bucketed by its start, its actual row sits in the later day's accounted total and can lower a presumed row on that day by at most that request's measured cost. (b) If Anthropic instead buckets by completion, a presumed row for a request that spanned midnight is compared with the earlier day, whose total may not hold the charge, and can be lowered too far; the same exposure has applied to every swept row since `782a853`, and is limited to presumed requests that span 00:00 UTC. (c) A backdated presumed row enters the rolling-cap window up to one request duration earlier, so with a rolling window shorter than a request it can leave the window sooner.
4. **A paid context-window stop** (AI-309). The pre-launch check estimates the input only. A request whose input fits the window but whose input plus the output ceiling does not is launched; the provider then stops the response with `model_context_window_exceeded`, the partial output is discarded, and the typed `context_window` error carries the cost of what was billed. The estimate is also calibrated on Metis payloads, not a ceiling (about 11% margin on the earlier tokenizer, about 5% on the current one); a prompt it admits wrongly is refused by the provider before any charge.
5. **A non-timeout connection failure before the response headers is released at $0, as at main** (D-next-1), for example ECONNRESET on an established socket. Only a request that timed out after it was sent, a stream lost after the headers, or a request answered and then cancelled is presumed. This is AI-307's purpose: one network blip must not book a presumed request maximum. `costs:reconcile` lowers presumed rows only, so a provider charge for such a request would be under-recorded until noticed. `tests/requestAdmission.test.ts` pins it ("pins that a connection reset before the response headers is released (D-next-1 limit)"). EHOSTUNREACH and ENETUNREACH count as never sent only from the connect syscall, and ETIMEDOUT only from the connect or name-lookup syscalls; the same codes from another syscall fall under this limit.
6. **An abort between the connection opening and the response headers is released** (D-next-1). Node's `fetch` does not report when the request body finished sending, so a request aborted in that gap may have been sent and is not recorded. The gap is a microtask; a timer-driven abort is unlikely to land there.
7. **A ledger write that stays contended** (AI-308, D-next-2). When every retry of the settlement write fails (three retries after the first try, waiting 250, 1,000 and 4,000 ms on top of the database's busy timeout on each try), the pass returns the response and states its cost, but no ledger row exists yet. The lease's expiry sweep later writes the lease's reserved request maximum as a presumed row, which can differ from the cost the pass stated. The provider tells the admission to abandon the permit, so the runner stops renewing that lease and it expires on schedule rather than counting against capacity for the rest of the pass. Only `costs:reconcile` can lower the row.
8. **`docs/audit/REMEDIATION-REPORT.md` (near line 315)** still says `both` "reconciles the section grades and scenario probabilities". It is a historical record of dated batches, left as written; the current rule is D-next-6.
9. **Version stamp deviation.** The audit listed `REPORT_SPEC_VERSION` for RPT-210. It is not moved: the audit export now prints a flag that every stored report already carried, and no field, grade, label or schema meaning changed. A bump would make every earlier report "not comparable" in the history diff although no financial convention changed. D-62 moved the whole cost breakdown into the audit export with the report spec and payload unchanged, and D-116 moved only the pipeline stamp for run-metadata changes. Only `PIPELINE_VERSION` moves, to `stage-c-1.6.10`.
10. **Two rare cases carried to batch 8** (D-next-1), which changes the same adapter. (a) When the charge at the final usage event is itself presumed (a reported model the registry does not know, or a refusal with no output and no category), the pass detail still describes a presumed remainder; the presumed flag and the figure are right. (b) With a reported model the registry does not know, an abandoned stream adds the output remainder to a figure already at the request maximum, so the row over-counts by up to one output remainder. Both over-state, never under-state, a cost.

Stored reports and artifacts keep their bytes.
